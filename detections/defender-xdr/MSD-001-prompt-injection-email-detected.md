# MSD-001 - Prompt-injection email detected by Defender for Office 365

| Field | Value |
|---|---|
| **ID** | MSD-001 |
| **Deployment target** | Microsoft Defender XDR advanced hunting |
| **Primary table** | `EmailEvents` |
| **Status** | **GA (no preview qualifier)** - see the status legend on the distinction. One Provisional element below: the `DetectionMethods` serialisation. |
| **Last verified** | 2026-08-15 |
| **MITRE ATLAS** | `AML.T0051` LLM Prompt Injection · `AML.T0051.001` LLM Prompt Injection: Indirect |

## Purpose

Surface inbound email that Microsoft Defender for Office 365 judged to carry prompt-injection
content, so a SOC can see attacks aimed at the AI assistant reading a mailbox rather than at the
person who owns it.

This is the one prompt-injection signal in this pack that sits on a generally available surface.
It is also the narrowest: it covers the **email channel only**.

## Schema this depends on

Every column below is quoted from the `EmailEvents` table reference on Microsoft Learn, read
2026-08-15, when the page's `ms.date` read 2026-08-03. **Re-read 2026-09-20, when the rendered
"Last updated on" date read 2026-09-02**, which is a second field rather than a later value of the
first: `ms.date` still read 2026-08-03 on that later read. The three value lists and the Streaming
API note were unchanged on that read, and the remaining rows were not re-enumerated.

**The trailing clause `SenderFromAddress` and `SenderFromDomain` share is Microsoft's own pairing.**
On the page the two FROM rows carry that clause and the two MAIL FROM rows carry a different one, so
the pairing goes by header rather than by adjacency, and the repetition between the two rows here is
published rather than a transcription slip. Confirmed against the live reference page on 2026-08-20.

The matched value, **`Prompt injection protection`**, is a documented detection-technology name. The
page that defines it is the email-entity detection-technology reference, not the prompt-injection
guide a reader would reach for first: its detection-technology table gives the row
"Prompt injection protection | Detection of prompt injection instructions hidden in inbound email
that target an AI assistant." The prompt-injection guide names the value and says where the
detection lands, which is the quote in the status evidence below.

> **One provisional element, and it decides how the query is written.** Learn types
> `DetectionMethods` as `string` and describes what it holds, but **does not document its value
> format** - whether a single message serialises one method, a delimited list, or JSON. The query
> below uses `has` rather than `==` for that reason. Confirm the actual serialisation in your own
> workspace before deploying (verification step 2).

> **A tenant emitted `DeliveryLocation` and `EmailDirection` values beyond the published lists
> on 2026-08-24, and this file is affected differently from MSD-002.** The lists above are
> Microsoft's, re-read 2026-08-24 and unchanged by that read. MSD-002 filters on both columns, and
> its `DeliveryLocation` filter matched nothing, which is recorded in that file along with the
> operator change it produced. Its `EmailDirection` filter was unaffected. **This file only projects them, and groups by `EmailDirection` in the rollup**, so an
> unlisted value here widens a result rather than emptying one: it appears in the projection, or as
> one more group in the rollup, instead of silently removing rows. **That is a difference in
> exposure and not a reason to relax.** Read the values your own workspace emits before writing any
> filter of your own on either column, and read MSD-002's note for what was observed.

## Query

```kusto
// MSD-001 - inbound email carrying prompt-injection content, per Defender for Office 365.
// Deployment target: Microsoft Defender XDR advanced hunting.
// Schema verified against Microsoft Learn on 2026-08-15. Verify DetectionMethods
// serialisation in your own workspace before converting this to a custom detection rule.
EmailEvents
| where Timestamp > ago(7d)
| where DetectionMethods has "Prompt injection protection"
| project
    Timestamp,
    ReportId,
    NetworkMessageId,
    SenderFromAddress,
    SenderFromDomain,
    RecipientEmailAddress,
    Subject,
    EmailDirection,
    ThreatTypes,
    DetectionMethods,
    ConfidenceLevel,
    DeliveryAction,
    DeliveryLocation
| order by Timestamp desc
```

**Why `Timestamp` and `ReportId` are both projected.** Microsoft's custom-detection-rules page
states: "To create a custom detection rule by using Defender data, we recommend that the query
returns the following columns", and for "all other Defender tables" - meaning every table outside
Defender for Endpoint - it says to "project `Timestamp` and `ReportId` from the same event to ensure
Defender identifies the original event that triggered the alert". It names the consequences of
leaving them out as alerts not being tagged with the correct entity scope and an alert timeline that
is not fully enriched. **That is a recommendation rather than a requirement**, and the page does not
say the rule wizard rejects a query without them - so read this as enrichment you give up, not as a
rule that will fail to save. **The heading and the sentence under it disagree in modality, and the
sentence is the one that governs.** The section is headed "Required columns in the query
results" and opens "To create a custom detection rule by using Defender data, we recommend that the
query returns the following columns", both read 2026-08-19. Both are recorded here because a reader
who meets the heading alone would reasonably take the columns for mandatory.

**The same page also says not to filter on those columns, and its own exception is the part that
matters here.** Verbatim: "Avoid filtering custom detections by using the `Timestamp` or
`TimeGenerated` column. The service prefilters data for custom detections based on the detection
lookback. Filter the results by `Timestamp` or `TimeGenerated` columns only if you want to add
additional filtering to ensure a specific sunset of the lookback window is evaluated." **The spelling
of "sunset" is the page's own.** Every shipped Defender XDR detection query in this pack filters on
`Timestamp`, which that third sentence makes the permitted narrowing rather than the discouraged
filtering - **provided the window sits inside the rule's lookback, and the query does not set the
lookback.** For Defender data the page fixes the lookback by rule frequency, the widest being 30 days
for a rule running every 24 hours, and it states that "Results outside of the lookback period are
ignored". **On those figures only the every-24-hours frequency has a lookback that reaches the
windows shipped here**, since every shipped Defender XDR detection query in this pack reaches back
seven days or thirty and the next widest lookback is 48 hours. It also states that custom detections
evaluate `ingestion_time()` rather than event timestamps, so "events with `Timestamp` or
`TimeGenerated` values older than the configured lookback period might still be included in the rule
evaluation". **The same page carries a second sentence about timestamps, and both are recorded here
because a reader who meets one alone would draw the wrong conclusion about the other.** Under its
**Rule frequency** heading it states, verbatim and re-read 2026-08-24: "The rule frequency is based
on the event timestamp and not the ingestion time." **The two are about different objects** on the
page's own arrangement, the frequency sentence sitting under **Rule frequency** and the
`ingestion_time()` sentence under the lookback material, so the first is about when a run happens and
the second about which events a run selects. **How those two interact for a query that compares a
long baseline against a short present is not stated on the page and was not tested for this pack**,
so it is a conversion-time check rather than a settled fact. Checklist Group 8 carries it.

### Triage pivot

```kusto
// Which senders and which recipients, over 30 days.
EmailEvents
| where Timestamp > ago(30d)
| where DetectionMethods has "Prompt injection protection"
| summarize
    Messages = dcount(NetworkMessageId),
    Recipients = dcount(RecipientEmailAddress),
    Payloads = dcount(EmailClusterId),
    FirstSeen = min(Timestamp),
    LastSeen = max(Timestamp)
    by SenderFromDomain, EmailDirection
| order by Messages desc
```

**What these two queries return stays in your environment, and they do not return the same things.**
The rule query projects sender and recipient identifiers, the sending domain and the subject line,
which is the most directly identifying output this pack produces. **The triage pivot returns less**:
it groups by the sending domain and the direction, and reduces recipients, messages and payloads to
counts, so it carries no subject line and names no individual recipient. **It does carry first-seen
and last-seen timestamps, and those are estate data as much as the addresses are**, which is the rule
MSD-008's verification step 2 states for the same pair. What travels outward is a column name or a
value name, never a result row, a row count, or anything inside one. **That default holds where a
column carries a closed set the platform defines, and `Subject` does not**: it is free text, so the
value is itself estate data and the default does not reach it, which is why the checklist carries
`EmailEvents.Subject` on its free-text list and why a subject line does not travel even as an
example. **Apply that reasoning to any other free-text column this query returns rather than looking
for it on a list**: the sender and recipient identifiers named above carry a description and no
published value set, exactly as `Subject` does. Checklist Group 0 states the same rule for every
step in the pack, and this file repeats it
because a reader who deploys one detection may never open the checklist.

## Status evidence

**GA (no preview qualifier)**, on this repository's status rule: a Microsoft Learn page carrying no
preview qualifier is the GA signal, and it is the weaker of the two GA classes in the legend.

- The Defender for Office 365 prompt-injection guide contains **no occurrence of the word
  "preview"** in the article body, which is the scope the search covered and the only scope it
  speaks to, as read on 2026-08-15 and re-read on 2026-08-17. The page's own
  stamp read 2026-08-06, a figure whose field was not recorded. Re-read 2026-09-29, the article body
  still contains no occurrence, its `ms.date` read 2026-09-02 and its rendered "Last updated on"
  date 2026-09-08.
- **The page names one plan, and it is Plan 2.** Its "Applies to" line, read 2026-08-16, is
  "Applies to: Microsoft Defender for Office 365 Plan 2, Microsoft Defender XDR". Its opening
  section says the same thing in a sentence, re-read 2026-08-17: "Microsoft Defender for Office 365
  Plan 2 detects prompt injection content in inbound email before that content reaches a user or an
  AI assistant." **The string "Plan 1" appears nowhere on the page** on either read. **If your
  tenant holds Plan 1 only, treat this detection as out of scope until Microsoft documents
  otherwise** - and note that this is a scope statement about the detecting product, not a licensing
  recommendation.
- That page states where the signal lands, verbatim: "Detections are classified under the existing
  **High confidence phishing** verdict with a new detection technology value: **Prompt injection
  protection**. Detection technology is a filterable property in Threat Explorer and real-time
  detections and Advanced Hunting."
- The `EmailEvents` table reference itself carries a standing prerelease disclaimer: "Some
  information relates to prereleased product which may be substantially modified before it's
  commercially released." That disclaimer is on the **table reference**, not on the
  prompt-injection capability, and the page does not say which columns it covers. It is recorded
  here rather than resolved.

## What this detection cannot see

Each limit below is scoped to a page that was read.

- **Prompt injection inside a Microsoft 365 Copilot chat conversation.** There is no documented
  advanced-hunting surface for Microsoft 365 Copilot chat prompts. See
  [`docs/verification-methodology.md`](../../docs/verification-methodology.md) for which pages were
  read to establish that and how far the claim extends.
- **Injection reaching an assistant from any grounding source other than email.** Per the
  Defender for Office 365 page, this control "inspects the email channel itself, before a message
  is ever delivered to a mailbox or read by an assistant." Files, SharePoint content, connectors,
  and web grounding are outside it.
- **Whether an AI assistant actually processed the message.** The table records the mail-flow
  verdict. It does not record that Copilot, an add-in, or an automation read the item.
- **Injection Defender did not judge as such.** A detection is evidence of a verdict, not a
  measure of coverage.

## False-positive guidance

- **Phishing-simulation and security-awareness platforms** send messages containing
  model-directed instruction text by design. Expect these to be a recurring source, and probably
  the largest one. Exclude by `SenderFromDomain` only after confirming the domain belongs to a
  platform you operate.
- **Security mail that quotes an injection payload** - vendor advisories, threat-intel
  newsletters, a forwarded incident thread, red-team reporting - carries the pattern legitimately.
- **Distribution-list expansion inflates row counts.** Learn describes `RecipientEmailAddress` as
  "Email address of the recipient, or email address of the recipient after distribution list
  expansion", so one message can produce many rows. Count with `dcount(NetworkMessageId)` rather
  than `count()`.
- **Forwarding is a different problem and needs a different column.** **That a forwarded message is
  a new message and receives a new `NetworkMessageId` is this pack's reading rather than something
  any page it cites states**: the schema table above carries Learn's whole published description of
  that column, "Unique identifier for the email, generated by Microsoft 365", and it settles no
  forwarding case. On that reading, grouping by it does nothing about forwards.
  Learn documents `EmailClusterId` as the "Identifier for the group of similar emails clustered
  based on heuristic analysis of their contents" - that is the field for "the same payload seen
  again". Use `NetworkMessageId` for distribution-list expansion and `EmailClusterId` for repeats.
- **Generic names on the same verdict.** The email carries the High confidence phishing verdict,
  which many other detection technologies also produce. Filter on `DetectionMethods`, not on
  `ThreatTypes` alone.

## Workspace verification before deployment

Run these before turning this into a custom detection rule. Full procedure in
[`checklists/workspace-verification-checklist.md`](../../checklists/workspace-verification-checklist.md).

1. Confirm the table exists and its columns match this file:
   `EmailEvents | getschema | project ColumnName, ColumnType`. **Diff that output against the schema
   table above.** Record as a **schema mismatch** any column the schema table lists which the output
   does not carry, or which the output types differently. **A column the output carries and the schema
   table does not is not a mismatch**, because the schema table is a deliberate subset. Then
   `EmailEvents | take 10` to confirm it returns rows.
2. Run `EmailEvents | where Timestamp > ago(30d) | summarize count() by DetectionMethods` and read
   the actual serialisation of the column. **Change the search literal to the form your workspace
   emits first, then choose the operator.** Doing it the other way round is the trap: swapping `has`
   for `contains` while still searching for `"Prompt injection protection"` returns zero rows against
   a value written `PromptInjectionProtection`, because the literal carries spaces the stored value
   does not - and a zero-row result here is the silent-empty state this file warns about.
   **`PromptInjectionProtection` here, and `Prompt_injection_protection` further down, are
   serialisation forms this pack wrote to illustrate the case rather than values Microsoft
   publishes**; the detection-technology page publishes the spaced form and no other.
   - a bare value, or a delimited list broken on word boundaries: keep the documented literal and
     keep `has`. Microsoft's string-operators reference defines `has` as matching where the
     right-hand side "is a whole term in" the left-hand side, and a term as one of the "maximal
     sequences of alphanumeric characters" a string value is broken into. **One thing that page does
     not settle, and this step is where it matters:** every example of `has` on it puts a single term on
     the right-hand side, and `Prompt injection protection` is three. Whether `has` matches a
     multi-term right-hand side at all was an assumption this pack could not verify from that page,
     re-read 2026-08-17, which documents neither behaviour. **The 2026-08-24 run tested it and a
     multi-term right-hand side matched**, on both surfaces, with all three of Group 2's positive
     controls true. **What that run did not do is separate the readings.** It did not exclude the
     reading on which the terms match while separated, which is the residual Group 2's own table
     names. Run this step anyway, and read it for what it now settles: the answer came from one
     tenant on one date, and **the run narrowed this question rather than closing it**, so the
     residual is smaller than the gap that first made this the step to run and the reason to check is
     weaker than it was. It is still a reason, because a reading on which the terms match while
     separated would widen what the operator matches without saying so
   - a value with no word boundary around the match, such as `PromptInjectionProtection`:
     **replace the literal with the form you observed, and only then decide whether the operator has
     to change**: where the observed form is itself a whole term, `has` matches it and no swap is
     needed. **`contains` is the operator only where what you must match is a fragment inside a
     longer alphanumeric run**, which replacing the literal cannot turn into a whole term; it is
     documented on the same page as matching where the right-hand side "occurs as a subsequence of"
     the left. That page gives the case verbatim: `"KustoExplorerQueryRun" has "Explorer"` "will
     return `false`" while `"KustoExplorerQueryRun" contains "Explorer"` "will return `true`", where
     `Explorer` is part of a longer run. **A form like `Prompt_injection_protection` is not an
     example of this case**, because the same page defines a term as a maximal sequence of
     alphanumeric characters and an underscore is not alphanumeric, so that form does break on word
     boundaries. **The swap has a cost the same page names**: a query that "uses a `contains`
     operator" will "revert to scanning the values in the column", and "Scanning is much slower than
     looking up the term in the term index". Make the swap because the stored value's shape requires
     it, not as a default
   - **more than one spelling in play, whatever the delimiter:** swapping `has` for `has_any` on the
     same single literal changes nothing, because the reference documents `has_any` as "Same as
     `has` but works on any of the elements". What it buys you is several spellings at once -
     `where DetectionMethods has_any ("Prompt injection protection", "<the form you observed>")`,
     which is the list form that page's own example uses. **Each element still inherits whatever
     `has` does with a multi-term right-hand side**, and the documented literal here carries more
     than one term, so if Group 2's test returns a false `MultiTerm` the multi-term element has to be
     split. **That cannot be done inside `has_any`.** The operator applies one behaviour to every
     element, so there is no way to give one element `has_all` semantics and another `has` semantics
     in a single clause, and adding the split terms to the list instead produces the over-match the
     next bullet warns about. **The shape is a disjunction:**
     `where DetectionMethods has_all ("Prompt", "injection", "protection") or DetectionMethods has "<the form you observed>"`.
     The single-term observed form keeps `has`, because splitting a single-term form into its
     constituent words across `has_all` gives a clause that cannot match it at all
   - **the multi-term literal does not match as a phrase**, which is the case checklist Group 2's
     test settles and the one none of the options above covers: split it across `has_all`,
     documented on the same page as "Same as `has` but works on all of the elements" with the worked
     example `"North and South America" has_all("south", "north")`. **The shape to run is
     `where DetectionMethods has_all ("Prompt", "injection", "protection")`**, which the 2026-08-24
     run did not exercise: the operator test it ran covers `has` with a multi-term right-hand
     side, not this split form. **`has_all` is order-independent and position-independent**, so it matches a
     value carrying all three terms in any arrangement and is weaker than a phrase match. **Against
     the published value set that weakness cannot bite**, because on the detection-technology page
     this pack cites, no published value other than the target carries `Prompt` or `injection`, so
     the only published value satisfying all three terms is the target itself. What the weakness is
     about is a value your own workspace emits that no page publishes. `has_any` is not the answer
     here: the same page documents it as
     working "on any of the elements", so `has_any ("Prompt", "injection", "protection")` would also
     match the published value `Antimalware protection`

   Do not leave `has` in place on the assumption it will work; it is term-based.
3. Confirm at least one row carries `Prompt injection protection`. If none does, you cannot tell
   from this query alone whether the capability is inactive or simply has had nothing to detect.
4. Confirm `EmailClusterId` is populated before relying on the forwarding guidance above:
   `EmailEvents | where Timestamp > ago(30d) | summarize Rows = count(), WithCluster =
   countif(isnotnull(EmailClusterId))`.
